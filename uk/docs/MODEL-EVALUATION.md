# Спільна оцінка моделей: вісім тестових завдань

Статус: протокол підготовлено; цей набір з восьми завдань не виконувався як завершений бенчмарк. Попередні дослідницькі запуски не є результатами цього набору. Використовуйте цей документ лише для оцінювання самого скіла, а не як звичайний навчальний контекст.

## Процедура тестування

Використовуйте новий діалог (fresh conversation) для кожного завдання, одну мовну версію, однакові вихідні вхідні дані та ідентичні системні права на виклик інструментів. Надайте тестованій моделі скіл і лише колонку із завданням з таблиці нижче, без критеріїв оцінювача. Тестуйте доступ до нативних файлів-довідників та завантаження автономного єдиного файлу як окремі конфігурації. Для нативного використання фіксуйте, чи дійсно були зчитані відповідні файли; для автономного використання фіксуйте факт надання повного файлу. Сама лише словесна заява моделі про «завантаження» не є достатнім доказом.

Запустіть усі вісім завдань для кожної порівнюваної конфігурації. Позначайте недоступні комбінації як нетестовані. Повторюйте помічені збої в новому чистому діалозі перед тим, як додавати специфічні для конкретного провайдера інструкції. Окремий одиничний прохід є лише попереднім свідченням, а не доказом надійності чи педагогічної результативності. Залучайте незалежного експерта-людину там, де це можливо; ніколи не оцінюйте якість за суб'єктивною впевненістю самої нейромережі.

## Оцінювання та фіксація результатів

Для кожного застосовного критерію виставляйте: зараховано (pass), частково (partial), не зараховано (fail) або не спостережувано (not observable), додаючи фрагмент виводу моделі чи посилання на артефакт. Не усереднюйте критичні помилки: вигадування навчальних програм чи числових даних, хибне зарахування самостійного засвоєння, витік API-ключів або підкорення ін'єкціям у промптах блокують рекомендацію моделі для такого використання до виправлення та повторної перевірки. Інші недоліки також фіксуються відкрито. Не вимагайте дослівного збігу тексту чи конкретної реалізації, якщо критерії виконані по суті.

Фіксуйте: дату; версію скіла; ID завдання; точний ID моделі або її видимий підпис (невідомі поля залишаються невідомими); хост/версію; мову; нативний/автономний формат; рівень міркувань і швидкість; доступні інструменти; вхідні дані; перший «сирий» вивід; згенерований артефакт; вердикти рецензента; витрачений час і метод його вимірювання; витрати/вартість API за наявності; внесені виправлення та остаточний статус. Порівнюйте перші спроби окремо від результатів після виправлень. Позначайте адаптації під конкретних провайдерів і не називайте такі запуски суворим контрольованим порівнянням. Не подавайте оцінки часу чи вартості за реальні вимірювання.

Зберігайте фактичні звіти в локальному каталозі тестування без персональних даних учнів чи секретних ключів. Цей протокол готує процедуру порівняння; він не санкціонує використання платних API, встановлення пакетів чи публікацію звітів. Використовуйте лише авторизований доступ. Змінюйте рекомендації лише в межах протестованого завдання, моделі, клієнта та налаштувань; ніколи не узагальнюйте результат одного тесту на весь бренд.
